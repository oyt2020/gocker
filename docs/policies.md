# Gocker Phase 2 운영 정책

- 기준: `phase2_clean` 브랜치, 커밋 `e8bf747` (2026-11-17)
- 관련 문서: [아키텍처](architecture.md), [상태 모델과 라이프사이클](lifecycle.md), [설계 결정 기록](decisions.md)

코드가 지키는 규칙을 주제별로 모았다. 왜 그렇게 정했는지는 [설계 결정 기록](decisions.md)에 있다.

## 1. 시그널과 종료

### 1.1 gocker가 받는 시그널

| 시그널 | 동작 |
|---|---|
| 첫 번째 SIGINT 또는 SIGTERM | ctx를 취소한다. 진행 중인 명령이 정리하고 반환할 기회를 준다 |
| 두 번째 SIGINT 또는 SIGTERM | 기본 동작으로 되돌아가 있으므로 gocker가 즉시 종료된다 |

`run -t`에서 키보드로 누른 Ctrl+C는 여기에 해당하지 않는다. 터미널이 raw 모드라 `0x03` 바이트로 PTY에 전달되고, 컨테이너 안에서 SIGINT가 된다.

### 1.2 취소되었을 때 명령별 동작

| 명령 | 취소 시 동작 | 레코드 |
|---|---|---|
| 포그라운드 `run` (컨테이너 실행 중) | 컨테이너를 중지하고 그 종료 코드로 끝난다 (1.4) | `STOPPED`, `exitCode` 기록 |
| `run`, `create` (생성 도중) | 생성을 중단하고 롤백한다 | 삭제 |
| `stop` (대기 중) | 즉시 에러로 반환한다 | 건드리지 않는다 |
| `rm` | runc 삭제가 중단되면 에러로 반환한다 | 남긴다 |

정리 작업(`--rm` 삭제, 시작 실패 후 삭제, 롤백의 runc 삭제, 취소 후 신호 전송)은 취소된 ctx를 쓰지 않는다. 취소된 뒤에도 끝까지 수행한다.

### 1.3 `stop` 절차

| 단계 | 동작 | 시간 |
|---|---|---|
| 0 | 이미 끝났으면 신호 없이 `STOPPED`를 기록하고 끝낸다 | |
| 1 | SIGTERM 전송 | |
| 2 | 종료 대기 | `-t` 값 (기본 10초), 200ms마다 확인 |
| 3 | 시간 초과 시 SIGKILL 전송 | |
| 4 | 종료 확인 | 최대 5초 |
| 5 | 그래도 살아 있으면 에러 | |

- `STOPPED`는 종료를 확인한 경우에만 기록한다.
- 취소, runc 조회 실패, 신호 전송 실패, SIGKILL 뒤에도 살아 있는 경우는 에러를 반환하고 레코드를 건드리지 않는다.
- 신호를 보내려는 순간 컨테이너가 스스로 끝났다면 신호 전송 실패로 보지 않는다.
- 신호는 컨테이너의 init 프로세스에만 보낸다.

### 1.4 포그라운드 `run` 취소 절차

| 단계 | 동작 | 시간 |
|---|---|---|
| 1 | SIGTERM 전송 | |
| 2 | 종료 대기 | 2초 |
| 3 | 끝나지 않았으면 SIGKILL 전송 | |
| 4 | 종료 대기 | 최대 5초 |
| 5 | 그래도 살아 있으면 에러 | |

- 받은 시그널이 SIGINT든 SIGTERM이든 컨테이너에는 SIGTERM을 보낸다.
- 취소는 에러가 아니다. gocker는 컨테이너의 종료 코드로 끝난다.
- SIGTERM 전송이 실패하면 기다리지 않고 바로 SIGKILL로 넘어간다.
- `stop`과 달리 runc를 폴링하지 않는다. gocker가 컨테이너의 부모이므로 `wait4`가 끝나는 순간이 곧 종료 시점이다.
- `--rm`이 있으면 이 절차가 끝난 뒤에 삭제한다.

### 1.5 종료 코드

| 상황 | gocker의 종료 코드 |
|---|---|
| 명령 성공 | 0 |
| gocker 자신의 에러 | 1 (stderr에 `gocker: ...` 출력) |
| 포그라운드 `run`, 컨테이너가 N으로 종료 | N |
| 포그라운드 `run`, 컨테이너가 시그널로 종료 | 128 + 시그널 번호 |
| `run -d` | 0 (컨테이너 ID 출력) |

컨테이너가 1로 끝난 것과 gocker의 에러는 종료 코드만으로는 구분되지 않는다. gocker의 에러는 stderr에 `gocker:`로 시작하는 메시지가 붙는다.

## 2. 실패 처리와 정리

원칙: **레코드가 남아 있는 한 `rm`으로 다시 정리할 수 있어야 한다.**

| 상황 | 동작 |
|---|---|
| 생성 도중 실패 | 만든 것을 역순으로 되돌린다 (runc 컨테이너 → 번들 → 레코드) |
| 롤백 도중 실패 | 거기서 멈춘다. 레코드가 남고, 에러에 "`gocker rm`으로 지우라"는 안내가 붙는다 |
| `run`에서 `start` 실패 | 컨테이너를 강제 삭제한다 |
| `rm` | runc 컨테이너 → 번들 → 레코드 순서로 지운다 |
| `rm` 도중 실패 | 거기서 멈추고 에러를 반환한다. 번들과 레코드는 남는다 |
| `rm`에서 runc 컨테이너나 번들이 이미 없음 | 정상으로 본다. 다음 단계로 넘어간다 |
| `--rm` 삭제 실패 | 에러로 보고한다. gocker는 컨테이너의 종료 코드가 아니라 1로 끝난다 |
| 종료 코드는 얻었지만 레코드 기록 실패 | 에러로 보고한다. gocker는 1로 끝난다 (런타임은 종료 코드와 에러를 함께 반환한다) |

- "이미 없음"만 정상으로 본다. 그 밖의 이유로 지우지 못했는데 다음 단계로 넘어가지 않는다.
- 정리 실패는 삼키지 않고 원래 에러에 합쳐서 반환한다.

### 여러 대상을 받는 명령

`start A B C`, `stop A B C`, `rm A B C`는 앞에서부터 차례로 처리한다.

- 하나가 실패하면 그 지점에서 멈춘다.
- 그 앞의 대상은 이미 처리된 상태로 남는다. 되돌리지 않는다.
- 성공한 대상은 한 줄씩 출력한다.

## 3. 동시성

여러 gocker 프로세스가 동시에 실행될 수 있다. 직렬화는 파일 잠금(`flock`)으로 한다.

| 잠금 | 파일 | 잡는 곳 | 범위 |
|---|---|---|---|
| 컨테이너 잠금 | `state/<id>.lock` | 생성 전체, `start`, `stop`, `rm`, 종료 코드 기록 | 컨테이너 하나 |
| 이름 잠금 | `state/names.lock` | 이름 중복 검사에서 레코드 기록까지 | 저장소 전체 |

- 조회(`ps`)는 잠금을 잡지 않는다.
- 컨테이너 참조(이름, ID 접두어)의 해석도 잠금 밖에서 한다. 해석 직후 컨테이너가 삭제되면 그 뒤 단계가 "찾을 수 없음"으로 실패한다.
- 두 잠금을 함께 잡을 때는 항상 컨테이너 잠금이 먼저다.
- 이름 잠금은 레코드를 쓴 직후에 푼다. rootfs 해제와 `runc create`는 이름 잠금 밖에서 한다.
- `stop`은 대기하는 동안 컨테이너 잠금을 쥐고 있다. 그동안 같은 컨테이너에 대한 다른 명령은 기다린다.
- 포그라운드 `run`은 컨테이너가 실행되는 동안 잠금을 쥐지 않는다. 그래서 다른 터미널에서 `stop`할 수 있다.

### 잠금 파일의 수명

- 레코드가 없는 ID의 잠금 파일은 잠금을 풀 때 지운다. 삭제가 끝난 컨테이너와 생성에 실패한 컨테이너의 잠금 파일이 남지 않는다.
- 이름 잠금 파일은 풀 때마다 지운다.
- 잠금을 기다리는 사이에 파일이 지워졌을 수 있다. 잠금을 잡은 뒤 경로가 여전히 같은 파일을 가리키는지 확인하고, 아니면 새 파일로 다시 시도한다.

### 레코드 쓰기

같은 디렉터리에 임시 파일을 쓰고 fsync한 뒤 rename한다. 쓰는 도중 중단돼도 기존 레코드는 온전하다.

## 4. 에러 분류

### runc 명령의 실패

| 순서 | 조건 | 결과 | 뜻 |
|---|---|---|---|
| 1 | ctx가 취소되었거나 만료됨 | ctx 에러를 감싼 에러 | 호출자가 중단시켰다. 컨테이너 상태에 대해 아무것도 알 수 없다 |
| 2 | stderr에 `does not exist`가 있음 | `runc.ErrNotFound` | runc가 그 컨테이너를 모른다. 프로세스도 없다 |
| 3 | 그 밖 | 원래 에러와 stderr | 알 수 없는 실패 |

ctx를 가장 먼저 확인한다. 취소로 runc가 죽으면 stderr의 내용은 믿을 수 없기 때문이다.

### `ErrNotFound`를 해석하는 곳

| 호출한 곳 | 해석 |
|---|---|
| `stop`의 종료 확인 | 종료된 것으로 본다 |
| `rm`의 runc 삭제 | 이미 지워진 것으로 보고 계속한다 |
| 조회 (`observe`) | 레코드가 `RUNNING`이면 `STOPPED`로 보여 준다. 그 밖에는 저장된 상태를 유지한다 |

### 런타임이 반환하는 에러 값

| 에러 | 조건 |
|---|---|
| `store.ErrNotFound` | 그 ID, 이름, 접두어에 해당하는 컨테이너가 없다 |
| `runtime.ErrNameInUse` | 같은 이름의 컨테이너가 이미 있다 |
| `runtime.ErrDetachWithRemove` | `Detach`와 `Remove`를 함께 지정했다 |
| `runtime.ErrStdinNotFile` | TTY 없이 연결하려는 표준 입력이 파일이 아니다 |

## 5. 거부하는 입력

| 입력 | 처리 |
|---|---|
| `run -d --rm` | 거부. 아무것도 만들지 않는다 |
| 이미 쓰이는 `--name` | 거부. 아무것도 만들지 않는다 |
| `stop -t 0`, 음수, 숫자가 아닌 값 | 거부. 컨테이너를 건드리지 않는다 |
| 대상 없이 `start`, `stop`, `rm` | 거부 |
| `ps`에 추가 인자 | 거부 |
| 4자 미만의 ID 접두어 | 일치로 인정하지 않는다 |
| 여러 컨테이너에 일치하는 참조 | 거부. 전체 ID를 쓰라고 안내한다 |
| `RUNNING` 컨테이너에 `-f` 없는 `rm` | 거부 |
| `STOPPED` 컨테이너에 `start` | 거부 |
| 정의되지 않은 플래그 | 거부 |

거부하지 않기로 한 것: `create -t`, `run -d -t` ([설계 결정 기록](decisions.md)의 16번).

## 6. 경로 안전

| 대상 | 규칙 |
|---|---|
| 컨테이너 ID | 12자리 소문자 16진수만 허용한다. 레코드, 잠금, 번들의 경로를 만들기 전에 검증한다 |
| 번들 디렉터리 | `os.OpenRoot`로 연 `containers/` 핸들을 통해 만들고 지운다. 그 밖으로 나갈 수 없다 |
| rootfs 아카이브 | 각 항목의 경로가 대상 디렉터리 안인지 검사한다. 심볼릭 링크를 거친 탈출은 막지 못한다 (미해결) |
